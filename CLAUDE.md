# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A reference implementation of a container deployment pipeline: Terraform-managed
AWS infrastructure + GitHub Actions CI/CD + a GitOps promotion flow where image-tag
bumps arrive as reviewable pull requests carrying a `terraform plan` in the PR
comments. **The infrastructure is the deliverable; the application is a fixture**
whose only jobs are to exercise every routing path the infrastructure defines and
to stay small. See `docs/APP-SPEC.md` for the full rationale.

This started as a take-home coding assignment; the goal now is a public
GitHub portfolio piece, with all third-party branding replaced. See
`docs/PRIORITIES.md` for the author's actual motivations, in priority order:
(1) hands-on DevOps/IaC experimentation and a template for future projects,
(2) a deliberate, cost- and skill-conscious experiment in agentic coding — so
default to focused, direct work over heavy multi-agent orchestration unless
asked, and (3) using the frontend fixture's visual (§6 of `APP-SPEC.md`) as a
genuine LLM-driven-art exercise, not filler. Priority 3 means that part of the
spec should be read as a real creative brief.

## Commands

**Terraform** — run from `infra/prod-aws` (the main stack) or 
`infra/prod-aws/bootstrap` (one-time state-bucket setup):

```bash
cd infra/prod-aws
terraform init
terraform fmt -recursive -diff
terraform validate
terraform plan
terraform apply
```

CI runs exactly this sequence (`aws-tf-plan.yaml` on PRs touching `infra/prod-aws/**`,
`aws-tf-apply.yaml` on merge to `main`) — reproduce plan output locally the same
way before pushing infra changes. `infra/prod-aws/bootstrap` is applied manually,
once, per the "Initial setup" steps in `infra/prod-aws/README.md`; it is not part of CI.

**Backend** (`app/`, stdlib-only Go, no external deps so no `go.sum`):

```bash
cd app
go vet ./...
go build -o /tmp/waypoint .
PORT=8099 /tmp/waypoint   # curl localhost:8099/healthz, /api/build, /api/runtime
```

**Full image build**, to exercise the actual `-ldflags` metadata injection:

```bash
docker build --build-arg GIT_SHA=$(git rev-parse --short HEAD) \
             --build-arg IMAGE_TAG=local --build-arg BUILD_TIME=$(date -u +%Y-%m-%dT%H:%M:%SZ) \
             -t waypoint:local .
docker run -p 8080:8080 waypoint:local
```

**Frontend** (`webapp/`, no build step by design): the frontend uses relative
fetch paths (`/api/build`), which only resolve correctly when something
serves both the static files and proxies `/api/*` to the backend on the same
origin — exactly what CloudFront does in production. A plain static file
server (`python3 -m http.server`) won't do that locally. Quickest local
option, backend already running per above:

```bash
cd webapp
npx http-server -p 8000 --proxy http://localhost:8080
```

(The `http://` scheme in `--proxy` is required — omitting it silently breaks
the fallback.)

## Architecture

### Traffic path

```
                    CloudFront
                   /          \
       default    /            \  /api/*
                 v              v
        S3 (static, OAC)    ALB (private, VPC origin)
                                     |
                                     v
                            ECS Fargate task (private subnet, no NAT)
```

Same-origin is achieved by CloudFront routing, not CORS — the frontend must
call the backend with relative URLs. The Fargate task has no public IP and no
NAT gateway; it reaches ECR and CloudWatch Logs exclusively through VPC
interface endpoints (`ecr.api`, `ecr.dkr`, `logs`) plus an S3 gateway endpoint
for ECR layer storage. All of this is defined in `infra/prod-aws/`, a single flat
Terraform stack (no modules) split across concern-based files — Terraform
concatenates every `.tf` in the directory, so the split is purely for humans:

- `main.tf` — `terraform`/`provider`/`locals` blocks and the resource group.
- `network.tf` — VPC, subnets, route table, the VPC endpoints, security groups.
- `edge.tf` — ALB/target group/listener/CloudFront origin and the S3 bucket +
  CloudFront distribution.
- `ecs.tf` — ECR, cluster, task execution role, task definition + service.
- `observability.tf` — log group, SNS alerts, unhealthy-target alarm, budget.
- `github-oidc.tf` — the OIDC provider and the four GitHub roles.

(These were carved out of what used to be one ~1100-line `main.tf`; file order
no longer matters since Terraform builds the graph from dependencies, so the
ECS task definition/service is not "deliberately last" anymore — it just lives
in `ecs.tf`.)

### GitOps pipeline (see `docs/ARCHITECTURE.md` for the full human-authored writeup)

1. A push to `main` touching the Dockerfile/app sources triggers
   `aws-build-push.yaml`: builds and pushes an image to ECR tagged with the
   short commit SHA, then opens a PR (via the default `GITHUB_TOKEN`, now that
   the repo allows Actions to create/approve PRs) that bumps `image_tag` in
   `infra/prod-aws/image.auto.tfvars`.
2. That PR does **not** auto-trigger `aws-tf-plan.yaml` — GitHub doesn't fire
   `pull_request` workflows off `GITHUB_TOKEN`'s own actions, to prevent
   recursive runs. Trigger it manually (`workflow_dispatch` against the PR's
   branch) to get a `terraform plan` posted as a PR comment before merging.
3. Merging the PR triggers `aws-tf-apply.yaml`, which runs `terraform apply`
   and rolls the ECS service to the new image.
4. Pushes touching `webapp/**` trigger `aws-frontend.yaml` independently —
   `aws s3 sync` plus a CloudFront invalidation, no Docker/Terraform involved.

Four distinct IAM roles back these workflows via GitHub OIDC, each scoped to a
specific `job_workflow_ref` so a workflow can only assume the role built for
it: `github_plan` (read-only), `github_push` (ECR push only), `github_apply`
(infra CRUD, explicitly denied any IAM self-modification — see the
`PassExecutionRoleOnly` statement and the comment above it in
`github-oidc.tf`), and
`github_frontend_deploy` (S3 sync + CloudFront invalidation only, no state
access, never touches `infra/`).

### Config file split

- `infra/prod-aws/terraform.tfvars` — personal/local config (`github_repo`,
  `github_oidc_subject_prefix`, `alert_email`), gitignored, not written by CI.
- `infra/prod-aws/image.auto.tfvars` — the one line CI rewrites every deploy
  (`image_tag`). Kept separate specifically so CI's writes and personal config
  never touch the same file.
- `infra/prod-aws/backend.tf` — generated by `infra/prod-aws/bootstrap`'s
  `local_file` resource, not hand-edited. Re-run bootstrap if the state bucket
  changes.
